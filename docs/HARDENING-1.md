Grand Hyatt Staff Accommodation Platform · 14 Oct 2026 · follows Stage 3, before Stage 4

Brief from the product owner: fix the identified gaps S-14, S-18, S-19, S-20, S-21, S-22; enforce role-based permissions, approval routing, separation of duties, audit logging, key-control rules, transfer eligibility and bed-readiness validation across all relevant workflows; preserve existing functionality; test the edge cases; update the SRS and the acceptance tests; **mark every newly proposed policy as pending client sign-off and do not silently assume it is approved.**

## How "pending sign-off" is built

- Every proposal is a numbered **P-item** in `docs/DECISIONS.md` section 15 (P-01 to P-14), in the SRS sign-off register (section 17) and in SRS Appendix C, with the setting that controls it.
- Every proposal has a **registry setting** with `proposed: 'P-xx'` (`src/server/config/registry.ts`); System configuration shows it as "Proposed, pending client sign-off". Changing it is a versioned, audited configuration change.
- **Default rule:** ON only where the code is made to match something already written down (APPROVALS.md, D-03, AT-021, SPEC-AMENDMENTS C-6); OFF (previous behaviour) where the proposal gives anyone new authority, adds a restriction or shows new data. **Every proposal is built and tested in both states.**
- Policy table additions that a proposal needs (`keys.report_own_lost`, Reception on `transfers_swaps.request`) exist in `policy.ts` with a comment, and the **command checks the setting**, so with the setting OFF the behaviour is exactly the old one.
